# 인증과 계정 복구

## 인증 기준선

서비스마다 고유하고 충분히 긴 비밀번호를 비밀번호 관리자에서 생성·보관한다. 임의의 복잡성 규칙이나 근거 없는 주기적 변경보다 유출·피싱·재사용을 줄이는 데 집중한다. 유출 정황, 공유 실수, 단말 침해가 있으면 즉시 변경하고 세션을 폐기한다.

지원된다면 피싱 저항성이 있는 패스키 또는 FIDO2 보안 키를 우선한다. TOTP와 문자 코드는 비밀번호만 쓰는 것보다 유용할 수 있지만, 사용자가 코드를 공격자 사이트에 입력하게 만드는 실시간 피싱에는 저항하지 못한다. 중요한 계정은 두 개 이상의 등록 수단을 서로 다른 장소에 보관한다.

## 세션과 복구

강한 로그인도 이미 발급된 세션 쿠키가 탈취되면 우회될 수 있다. 활성 세션, 신뢰 기기, OAuth 연동 앱, 앱 비밀번호를 정기 검토하고 사건 시 전체 세션을 폐기한다.

복구 채널은 인증의 뒷문이 아니라 동일한 보안 경계다. 복구 이메일·전화·백업 코드를 독립적으로 보호하고, 지원센터가 요구하는 정보와 계정 잠금 절차를 미리 확인한다. 복구 코드와 비밀번호 데이터베이스를 같은 단말·같은 클라우드 계정에만 두지 않는다.

## 1. 보호 목표와 실패 모델

인증의 목표는 계정 소유자를 ‘완벽하게 증명’하는 것이 아니라, 승인되지 않은 주체가 계정·세션·복구 수단을 장악하기 어렵게 하고 장악 정황을 발견·철회·복구할 수 있게 하는 것이다. 인증 성공 이후 서비스가 과도한 권한을 주거나 세션을 오래 유지하면 강한 로그인도 전체 위험을 해결하지 못한다.

다음 실패를 별도로 모델링한다.

1. 유출된 암호의 재사용과 자동 대입
2. 가짜 로그인 페이지와 실시간 중계 피싱
3. 악성코드·브라우저 확장에 의한 암호·세션 탈취
4. SIM 교체, 번호 재할당과 SMS 가로채기
5. TOTP 시드·백업·화면 캡처 유출
6. 보안 키 분실·고장과 예비 수단 부재
7. 복구 이메일·전화·지원센터를 통한 우회
8. OAuth 앱, 앱 비밀번호와 API 토큰의 장기 접근
9. 관리자·공급자에 의한 재설정 또는 로그 접근
10. 지나치게 복잡한 통제로 사용자가 MFA를 끄거나 암호를 공유하는 운영 실패

계정별로 기밀성·무결성·가용성과 파급 범위를 평가한다. 이메일, 암호 관리자, 통신사, 도메인 등록자와 조직 ID는 다른 계정을 복구하거나 가장할 수 있으므로 **루트 계정**으로 분류한다.

## 2. 계정 계층과 우선순위

### 2.1 루트 계정

기본 이메일, Bitwarden 등 암호 관리자, Apple·Google·Microsoft 플랫폼 계정, 이동통신 계정, 도메인·DNS, 조직 SSO와 관리자 계정은 장악 시 여러 자산으로 확장된다. 가장 강한 MFA, 별도 복구 경로, 활성 세션 검토와 신속 알림을 우선 적용한다.

### 2.2 중요 업무 계정

코드 저장소, 클라우드, 결제·금융, 메신저 관리자, 고객 데이터와 배포 계정은 권한과 토큰 수를 최소화한다. 일상 사용자와 관리자 계정을 분리하고, 관리 작업에는 별도 브라우저 프로필 또는 단말·VM을 사용한다.

### 2.3 일반·저위험 계정

일회성 포럼과 뉴스레터에도 암호 재사용은 하지 않는다. 다만 모든 계정에 동일한 고비용 절차를 강제하면 관리 불가능해진다. 암호 관리자의 고유 암호와 서비스가 지원하는 실용적 MFA를 기준선으로 두고, 폐기 가능한 계정은 복구 비용보다 최소 정보 제공을 우선할 수 있다.

### 2.4 역할 분리 계정

실명·조직·가명 역할을 분리하려면 계정 이름뿐 아니라 복구 이메일, 전화번호, 브라우저, 보안 키 등록, 결제, 로그인 시간과 연락망을 검토한다. 같은 Bitwarden 볼트나 동기화형 패스키를 쓰는 사실이 서비스 외부에 직접 공개되지 않더라도, 단말 침해와 운영 실수의 공통 실패가 된다. 위협이 높으면 역할별 볼트·프로필·장치를 검토한다.

## 3. 비밀번호 설계

### 3.1 길이·고유성·무작위성

“대문자·소문자·숫자·특수문자 16자리” 같은 형식 규칙만으로는 충분하지 않다. `Password1!Password1!`처럼 긴 패턴은 예측 가능하고, 서비스마다 같은 암호를 쓰면 한 번의 유출이 확산된다. 암호 관리자가 생성한 고유 무작위 암호를 기본으로 한다.

사용자가 직접 기억해야 하는 암호 관리자 마스터 암호나 디스크 암호는 여러 임의 단어로 구성한 긴 패스프레이즈를 고려한다. 사전 단어를 사람이 의미 있게 고르면 예측 가능성이 커질 수 있으므로 신뢰할 수 있는 생성 방식을 사용한다. 조직이 무리한 정기 변경과 복잡성 규칙을 강제해 사용자의 메모·재사용을 유발하지 않는지 점검한다.

### 3.2 변경 시점

근거 없는 짧은 주기 변경보다 다음 사건에 대응한 변경을 우선한다.

- 서비스나 관련 계정의 침해·유출 통보
- 피싱 페이지 입력 또는 잘못된 공유
- 악성코드·브라우저 확장·원격 제어 의심
- 동일·유사 암호가 다른 계정에 사용된 사실 발견
- 담당자 퇴사·역할 변경과 공유 비밀 회수
- 서비스의 암호 해싱·정책 결함 또는 관리자 요청

변경 후에는 기존 세션, 앱 비밀번호, API 토큰과 OAuth 권한을 함께 철회한다. 암호만 바꾸고 공격자의 세션이 유지되면 대응이 끝나지 않는다.

### 3.3 유출 확인

서비스의 공식 침해 통보와 신뢰할 수 있는 유출 확인 기능을 사용하되 암호 원문을 임의 사이트에 입력하지 않는다. 브라우저·암호 관리자의 유출 경고가 어떤 데이터와 방식으로 조회하는지 공식 문서로 확인한다. 유출되지 않았다는 결과는 계정이 안전하다는 증명이 아니다.

## 4. Bitwarden과 암호 관리자

Bitwarden 같은 암호 관리자는 고유 암호 생성과 자동 완성, 안전한 공유를 가능하게 하는 동시에 볼트·계정·복구가 집중된 고가치 자산이 된다. 공격자는 개별 암호보다 마스터 계정, 브라우저 확장, 내보내기와 복구 경로를 우선 노릴 수 있다.

### 4.1 도입 평가

- 클라우드형, 자체 호스팅 또는 로컬형 중 누가 운영과 복구를 책임지는가?
- 암호화·키 파생과 볼트 잠금 방식이 현재 공식 문서에 명시되는가?
- 웹 볼트, 브라우저 확장, 모바일·데스크톱 앱의 공격 면과 업데이트가 관리되는가?
- 조직 공유, 감사 로그, 관리자 복구와 사용자 프라이버시의 경계가 적합한가?
- 내보내기 형식과 암호화 백업, 비상 접근과 계정 상속을 지원하는가?

자체 호스팅은 공급자 의존 일부를 줄일 수 있지만 패치, TLS, 백업, 가용성, 이메일과 관리자 보안 책임을 조직에 옮긴다. 운영 역량 없이 ‘자체 호스팅이 더 안전하다’고 가정하지 않는다.

### 4.2 마스터 암호와 MFA

볼트 마스터 암호는 다른 곳에 쓰지 않는 긴 패스프레이즈로 하고, 계정에는 FIDO2/WebAuthn 보안 키 또는 지원되는 강한 MFA를 적용한다. 마스터 암호와 복구 코드, 보안 키를 같은 가방·같은 클라우드에만 두지 않는다. 장치의 생체 잠금은 로컬 편의 기능이며 서버 계정의 마스터 암호와 동일한 역할이 아니다.

### 4.3 브라우저 확장

자동 완성은 도메인 일치를 통해 피싱을 발견하는 보조 신호가 될 수 있지만, 유사 도메인·iframe·침해된 정상 사이트와 확장 자체의 취약점을 고려한다. 모든 필드 자동 채우기보다 사용자 동작을 요구하는 설정을 검토하고, 민감 계정은 URL과 표시된 서비스명을 확인한다. 클립보드 복사는 다른 앱·기록에 노출될 수 있으므로 자동 삭제와 사용 최소화를 고려한다.

### 4.4 공유와 조직 볼트

팀 암호를 개인 메모·메신저로 공유하지 않고 조직 컬렉션과 역할 권한을 사용한다. 누가 비밀을 볼 수 있는지, 퇴사 시 접근과 로컬 캐시가 어떻게 처리되는지, 변경 이력이 남는지 확인한다. 가능하면 공유 암호 대신 개인 계정·SSO·단기 토큰과 비밀 관리 시스템을 사용한다.

### 4.5 내보내기와 복구

볼트 내보내기는 평문 파일이 될 수 있으므로 형식과 저장 위치를 확인한다. 암호화된 오프라인 백업, 버전·복원 시험, 생성 후 평문 임시 파일과 휴지통 처리를 문서화한다. 비상 접근을 설정하면 대기 시간, 승인·거부, 알림과 수신자의 계정 보안을 검토한다.

## 5. 인증 수단 비교

### 5.1 SMS와 음성 코드

SMS MFA는 번호 재할당, SIM 교체, 통신사 고객센터 공격, 메시지 전달과 실시간 피싱에 취약할 수 있다. 더 강한 수단을 지원하는 루트·관리자 계정에서는 우선순위를 낮춘다. 그러나 MFA가 전혀 없는 것보다 위험을 낮추는 상황도 있으므로 일률적 금지로 사용자가 MFA를 끄게 하지 않는다. 통신사 계정 PIN, 번호 이동 잠금과 변경 알림을 설정한다.

### 5.2 이메일 코드

이메일이 같은 계정의 복구 수단이면 이메일 장악이 인증 우회로 이어진다. 코드가 전달되는 메일 계정에 더 강한 MFA를 적용하고, 메일 세션과 자동 전달 규칙을 점검한다. 업무 메일과 개인 복구 메일의 관리자 경계를 확인한다.

### 5.3 TOTP

TOTP는 공유 시드와 시간을 이용해 짧은 코드를 생성한다. 오프라인으로 작동하고 널리 지원되지만 사용자가 가짜 사이트에 코드를 입력하면 공격자가 즉시 중계할 수 있다. 시드 QR 화면, 앱 백업, 내보내기 파일, 클라우드 동기화와 스크린샷은 장기 비밀로 보호한다.

### 5.4 푸시 승인

푸시 MFA는 편리하지만 반복 요청을 통한 피로 공격과 무심코 승인하는 위험이 있다. 숫자 일치, 로그인 위치·장치 표시와 사용자 신고 기능을 사용한다. 사용자가 시작하지 않은 요청은 거부하고 비밀번호 변경·세션 검토를 수행한다.

### 5.5 FIDO2/WebAuthn 보안 키와 패스키

FIDO2/WebAuthn은 검증자 도메인과 자격 증명을 결합해 일반적인 중계 피싱 저항성을 높인다. YubiKey, Nitrokey 등 물리 보안 키와 플랫폼·동기화 패스키는 저장·복구 모델이 다르다. 서비스가 정확히 무엇을 지원하는지, 등록 가능한 키 수, 사용자 확인 PIN·생체, 장치 귀속 여부와 복구 절차를 확인한다.

패스키가 동기화되면 장치 분실 복구는 쉬워질 수 있지만 플랫폼 계정과 클라우드 복구가 새로운 신뢰 경계가 된다. 장치 귀속 자격 증명은 복제 위험을 줄이는 대신 예비 키와 관리자 복구가 더 중요하다.

### 5.6 클라이언트 인증서·PIV·스마트카드

조직 단말·VPN·관리자 로그인에는 인증서와 PIV 스마트카드를 사용할 수 있다. 발급, PIN, 인증기관, 폐기 목록, 장치 분실과 만료 갱신을 운영해야 한다. 카드가 꽂힌 잠금 해제 세션과 악성 단말을 별도로 고려한다.

## 6. Authy, Aegis, Google Authenticator 평가

Google Authenticator, Authy와 Aegis는 배포 모델, 플랫폼, 백업·내보내기와 계정 복구가 다르며 기능도 변할 수 있다. 앱 이름만으로 금지·허용하지 않고 다음 질문으로 평가한다.

1. TOTP 시드를 로컬에서 어떻게 암호화하고 앱 잠금을 제공하는가?
2. 기기 교체를 위한 내보내기·백업은 가능한가? 형식은 평문인가 암호화되는가?
3. 클라우드 동기화를 사용하면 어떤 계정과 전화번호·이메일에 의존하는가?
4. 다중 기기 기능을 끄거나 새 장치 등록을 감시할 수 있는가?
5. 오픈소스 여부, 빌드·배포 출처와 업데이트 주기는 어떠한가?
6. 앱을 잃었을 때 서비스별 복구 코드 없이 복원할 수 있는가?
7. 지원 종료나 계정 정책 변경 시 다른 앱으로 이전할 수 있는가?

### 6.1 Authy

Authy는 다중 플랫폼·백업 기능 때문에 편리할 수 있지만 전화번호·서비스 계정·클라우드 백업의 신뢰와 복구 절차를 평가해야 한다. 사용 중인 플랫폼의 현재 지원 상태와 다중 기기 등록 정책을 공식 문서로 확인한다. 백업 암호를 잃거나 약하게 설정하는 위험, 계정 탈취와 번호 재할당을 함께 본다.

### 6.2 Aegis

Aegis는 Android 중심 TOTP/HOTP 관리 앱 사례다. 로컬 볼트, 암호화 내보내기와 생체 잠금 등 실제 사용 버전의 기능을 공식 프로젝트 문서에서 확인한다. 오픈소스라는 사실만으로 설치 파일의 진위와 단말 무결성이 보장되지는 않는다. F-Droid·공식 배포 출처와 서명을 검토한다.

### 6.3 Google Authenticator

Google Authenticator는 널리 지원되는 TOTP 앱이며 동기화·이전 기능의 동작과 계정 의존성을 현재 공식 도움말로 확인한다. 과거 기능 인식만으로 금지하지 않는다. Google 계정과 역할을 분리해야 하는 환경에서는 동기화 여부와 복구 경계를 고려한다.

### 6.4 이전 절차

앱을 바꿀 때 하나의 QR을 여러 앱에 동시에 등록해 장기간 복제된 시드를 남기지 않는다. 서비스별로 새 시드를 발급하고 이전 시드를 무효화하며, 새 앱과 복구 코드를 시험한다. 화면 캡처·내보내기 파일·프린트물의 잔존 사본을 처리한다. 서비스가 시드 교체를 지원하지 않으면 MFA를 해제한 짧은 구간의 위험과 재등록 순서를 계획한다.

## 7. YubiKey, Nitrokey와 예비 키

YubiKey와 Nitrokey는 모델별 지원 프로토콜과 인터페이스가 다르다. 구매 전 FIDO2/WebAuthn, OTP, PIV, OpenPGP, USB-C/A, NFC, 생체·FIPS 요구를 정확한 모델 공식 문서와 대조한다. 하나의 키를 모든 역할과 조직에 등록하면 분실이라는 공통 실패와 역할 연결 가능성이 생긴다.

루트 계정에는 최소 두 개의 독립 보안 키를 등록한다. 주 키는 일상 사용, 예비 키는 별도 안전 위치에 보관한다. 예비 키도 분기별 실제 로그인으로 확인하고 펌웨어·PIN·라벨을 관리한다. 키 라벨에 이메일·조직명 같은 민감 정보를 그대로 쓰지 않고 내부 자산 ID를 사용할 수 있다.

분실 시 해당 키가 등록된 서비스 목록을 즉시 찾을 수 있어야 한다. 서비스별로 키를 철회하고 세션·복구 수단을 검토한다. 물리 키를 찾았더라도 통제 밖에 있었고 PIN 노출 가능성이 있다면 재등록 여부를 위험에 맞게 결정한다.

## 8. 패스키 운영 모델

패스키 도입 전 다음 세 모델을 구분한다.

- **동기화형**: 플랫폼 계정을 통해 여러 장치에 동기화된다. 사용성과 복구가 좋을 수 있으나 플랫폼 계정과 복구가 핵심 경계가 된다.
- **장치 귀속형**: 특정 장치·보안 키에서만 사용할 수 있다. 복제 저항성이 높을 수 있으나 분실 대비가 필요하다.
- **관리형 기업 자격 증명**: 조직 정책, 장치 등록과 관리자 복구에 종속된다. 퇴사·장치 교체·비상 접근을 정의해야 한다.

서비스가 “패스키”라고 표시해도 사용자 이름 없는 로그인, 사용자 확인, 동기화, 내보내기와 폴백 방식이 다를 수 있다. 비밀번호·SMS 폴백이 그대로 열려 있으면 전체 보안은 가장 약한 복구 경로에 의해 제한된다.

## 9. 계정 복구 설계

### 9.1 복구 수단 목록화

계정마다 복구 이메일, 전화, 백업 코드, 예비 보안 키, 신뢰 장치, 관리자 재설정, 고객 지원과 신원 확인 서류를 기록한다. 실제 비밀은 대장에 넣지 않고 위치·소유자·마지막 시험일을 기록한다.

### 9.2 독립성

암호 관리자 암호와 복구 코드를 그 암호 관리자 안에만 두면 잠금 시 접근할 수 없다. 이메일 계정의 복구 이메일이 서로 순환하면 한 계정 장악이 확산된다. 예비 키, 인쇄 또는 암호화된 복구 코드, 별도 위치의 백업을 위험에 맞게 둔다.

### 9.3 지원센터

서비스의 공식 복구 절차와 요구 정보, 예상 시간, 계정 잠금과 거부 이의 절차를 사전에 확인한다. 조직 관리자는 전화·메신저 요청만으로 MFA를 초기화하지 않고 티켓, 신원 확인, 이중 승인과 사후 알림을 사용한다. 고위험 관리자 복구는 시간 지연과 다른 관리자 검토를 고려한다.

### 9.4 비상 접근과 상속

장기 부재·사망·의료 비상 시 필요한 계정과 데이터만 지정된 사람이 접근하도록 설계한다. 모든 개인 메시지와 암호를 무조건 공유하는 방식보다 문서·자산별 권한, 대기 시간, 취소와 감사 기록을 사용한다. 현지 상속·고용·개인정보 법률은 전문가와 확인한다.

## 10. 세션, 토큰과 연동 앱

로그인 후 발급되는 세션 쿠키는 비밀번호와 MFA를 거치지 않고 요청을 인증할 수 있다. 브라우저 동기화, 악성 확장, 인포스틸러, 공유 컴퓨터와 지원 도구가 세션을 탈취할 수 있다. 중요한 계정은 활성 세션의 장치·위치·생성일을 검토하고 사용하지 않는 세션을 종료한다.

OAuth 연동 앱은 암호를 모르더라도 메일·파일·프로필에 접근할 수 있다. 앱 이름, 게시자, 권한, 마지막 사용, 토큰 만료와 관리자 동의를 검토한다. 앱 비밀번호, 개인 액세스 토큰, API 키와 SSH 키도 계정 자격 증명 대장에 포함하고 목적·소유자·만료·마지막 사용을 기록한다.

사고 시 암호 변경, 세션 종료, 토큰 철회, 메일 전달 규칙·필터, 로그인 방법, 복구 연락처와 새 관리자 계정을 함께 확인한다. 공격자가 만든 지속성 하나를 놓치면 다시 장악될 수 있다.

## 11. 조직 운영 기준

### 11.1 가입

개인별 계정을 발급하고 공유 계정을 최소화한다. 초기 자격 증명은 만료되는 안전한 채널로 전달하고 최초 로그인에서 강한 MFA와 예비 수단을 등록한다. 관리자·재무·코드 배포 역할은 별도 승인을 요구한다.

### 11.2 변경

부서·직무 변경 시 기존 그룹과 토큰을 제거한 뒤 새 권한을 부여한다. 임시 권한에는 만료를 설정한다. 관리자가 자기 권한을 승인하지 않도록 역할을 분리하고 정기 접근 검토에서 실제 업무 필요를 확인한다.

### 11.3 퇴사·종료

예정·긴급 종료에 맞춰 계정 비활성화, 세션·토큰 철회, 보안 키·장치 회수, 공유 비밀 교체, 메일·파일 인계와 보존을 수행한다. 사용자의 개인 계정이나 데이터에 부당하게 접근하지 않고 조직 자산 경계를 사전에 명확히 한다.

### 11.4 관리자 비상 계정

일상 SSO 장애에 대비한 비상 계정은 매우 제한적으로 두고 강한 장치 귀속 자격 증명, 봉인된 복구, 로그인 알림과 사용 후 자격 증명 교체를 적용한다. 비상 계정을 일반 자동화나 일상 관리에 쓰지 않는다.

## 12. 탐지와 사고 대응

다음 신호를 수집하되 과도한 직원 감시나 불필요한 위치 보존을 피한다.

- 새 장치·새 MFA·복구 연락처 등록
- 불가능한 이동 또는 평소와 다른 국가·네트워크의 로그인
- 반복 실패, MFA 피로 요청, 보안 키 등록 실패
- 관리자 권한 상승과 새 OAuth 동의
- 대량 다운로드·메일 전달 규칙·API 토큰 생성
- 비밀번호·복구·SIM·도메인 설정 변경

의심 이벤트는 사용자에게 독립 채널로 확인한다. 단순 위치 이상은 VPN·이동 때문에 오탐일 수 있으므로 계정 잠금의 업무 영향을 고려한다. 고신뢰 침해에서는 세션·토큰을 먼저 차단하고 깨끗한 장치에서 암호·MFA·복구 수단을 재설정한다.

## 13. 구축 절차

1. 전체 계정을 수집하고 루트·중요·일반·폐기 대상으로 분류한다.
2. 재사용 암호를 암호 관리자 생성 고유 암호로 바꾼다.
3. 이메일·암호 관리자·통신사·관리자 계정부터 피싱 저항 MFA를 적용한다.
4. 주·예비 보안 키와 복구 코드를 서로 다른 위치에 둔다.
5. 사용하지 않는 로그인 방법, 세션, OAuth 앱과 토큰을 제거한다.
6. Authy·Aegis·Google Authenticator 등 TOTP 앱의 백업·이전 경계를 문서화한다.
7. 조직은 입사·변경·퇴사와 관리자 복구 절차를 시험한다.
8. 분실·단말 교체·암호 관리자 잠금을 가정한 복구 훈련을 수행한다.

## 14. 검증 기준

- 루트 계정마다 고유 암호, MFA, 예비 수단과 독립 복구 경로가 있는가?
- 주·예비 YubiKey 또는 Nitrokey로 실제 로그인했는가?
- 보안 키 하나를 시험 계정에서 철회했을 때 재사용이 거부되는가?
- TOTP 앱 백업을 새 시험 장치에서 복원하거나 서비스별 재등록할 수 있는가?
- Bitwarden 볼트 잠금·내보내기·복구 절차가 평문을 방치하지 않는가?
- 암호 변경 뒤 기존 세션·OAuth 토큰과 앱 비밀번호가 의도대로 철회되는가?
- 복구 이메일·전화와 지원센터 절차가 원래 인증보다 현저히 약하지 않은가?
- 담당자 부재 시 승인된 사람이 문서만으로 핵심 계정을 복구할 수 있는가?

## 15. 실패 판정과 잔여 위험

다음 중 하나면 강한 인증이 구축됐다고 판정하지 않는다.

- 보안 키는 하나뿐이고 복구 코드는 같은 가방에 있다.
- MFA를 등록했지만 SMS·지원센터 폴백이 아무 통제 없이 남아 있다.
- 공유 관리자 암호를 여러 사람이 알고 퇴사 후 교체하지 않는다.
- TOTP 시드 QR과 볼트 내보내기가 사진·다운로드 폴더에 남는다.
- 암호 변경 후 공격자 세션과 OAuth 앱을 검토하지 않는다.
- 조직이 사용자의 MFA 초기화를 전화 한 통으로 승인한다.
- 복구 시험을 한 적이 없고 계정 제공자의 최신 정책을 모른다.

FIDO2와 패스키도 악성 단말, 이미 탈취된 세션, 서비스 내부자, 사용자가 승인한 악성 OAuth 앱과 수신자 공개를 막지 않는다. 암호 관리자는 집중 위험과 복구 의존성을 만든다. 인증은 장치 보안, 최소 권한, 세션 탐지, 백업과 사고 대응과 함께 운영한다.

## 검증

실제 계정을 위험에 빠뜨리지 않는 범위에서 연 2회 복구 절차를 연습한다. 보안 키 분실, 휴대전화 교체, 비밀번호 관리자 잠금, 담당자 부재를 가정하고 복구 시간과 실패 지점을 기록한다.
