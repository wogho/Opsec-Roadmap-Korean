# 저장 암호화와 키관리

> 저장 암호화는 데이터를 없애는 기술이 아니라, 정당한 키를 제시하지 않은 주체가 평문에 도달하는 비용을 높이는 통제다. 설계의 중심은 알고리즘 이름이 아니라 보호 상태, 키 수명주기, 복구 가능성, 잠금 해제 이후의 노출과 운영자의 행동이다.

## 1. 공격자 관점의 보호 범위

공격자는 암호 알고리즘을 정면으로 깨기보다 잠금 해제된 단말, 약한 복구 경로, 키 백업, 마운트된 볼륨, 관리자 권한과 수신자 사본을 노린다. Nitrokey Storage 2, YubiKey, VeraCrypt, BitLocker, FileVault, LUKS와 모바일 장치 암호화는 보호 계층과 실패 상태가 서로 다르므로 저장·인증·복구 기능을 분리해 평가한다.

- **Nitrokey Storage 2**는 암호화 저장소와 스마트카드 기능을 결합한 특정 세대의 장치다. 일반적인 FIDO2 보안 키와 목적이 같지 않다.
- **Nitrokey 3·YubiKey 계열**은 모델과 애플리케이션에 따라 FIDO2/WebAuthn, OTP, OpenPGP, PIV 등 서로 다른 인증 기능을 제공한다. 보안 키에 일반 파일을 저장한다는 뜻이 아니다.
- **VeraCrypt**는 볼륨·컨테이너 또는 지원되는 시스템 암호화를 제공하지만, 마운트된 볼륨과 감염된 단말을 보호하지 않는다.
- **BitLocker·FileVault·LUKS/dm-crypt와 모바일 장치 암호화**는 운영체제와 결합된 저장 보호다. 제품명을 이유로 일률적으로 금지하거나 안전하다고 선언할 수 없다.
- **전원 차단**은 잠금 해제된 상태의 노출 시간을 줄일 수 있지만 증거 보전, 가용성, 파일시스템 무결성, 메모리·주변기기 상태까지 고려해야 하는 사고 대응 결정이다. 이른바 ‘패닉 버튼’이나 파괴 기능을 기본 통제로 권고하지 않는다.

보호 목표는 장치를 잃거나 저장매체가 복제돼도 키를 제시하지 않은 주체가 평문에 도달하기 어렵게 하는 것이다. 잠금 해제 이후의 악성코드·세션·화면·수신자 노출은 별도 통제로 다룬다.

## 2. 먼저 구분해야 할 보호 상태

암호화의 효력은 장치 상태에 따라 달라진다. 문서와 시험 기록에는 단순히 “암호화됨”이 아니라 다음 상태를 표시한다.

| 상태 | 예상되는 보호 | 남는 주요 위험 |
|---|---|---|
| 전원 꺼짐·정상 종료 | 키가 별도 보호되고 강한 인증을 쓴다면 오프라인 추출 저항 | 약한 암호, 복구키 유출, 펌웨어·부팅 체인 변조, 백업 평문 |
| 부팅 후 최초 잠금 해제 전 | 플랫폼별 ‘사용자 인증 전’ 데이터 보호 | 복구 경로, 주변기기, 부팅 구성, 원격 관리 정책 |
| 로그인 후 화면 잠금 | 일상적 접근을 제한하지만 키와 세션이 메모리에 남을 수 있음 | 악성코드, DMA·주변기기, 관리자, 이미 열린 세션 |
| 볼륨 마운트·파일 열림 | 정상 애플리케이션이 평문을 사용 | 화면·클립보드·임시 파일·스왑·로그·동기화·수신자 |
| 공유·백업 완료 | 수신자와 백업 체계의 통제에 종속 | 사본 확산, 보존 기간, 삭제 불일치, 계정 탈취 |

전체 디스크 암호화는 주로 분실·절도된 **꺼진 장치**를 다룬다. 파일 암호화는 데이터 단위의 별도 경계를 만든다. 전송 암호화는 네트워크 구간을, 종단간 암호화는 통신 참여자 사이를 다룬다. 이 셋은 대체재가 아니다.

## 3. 위협 모델과 요구사항

암호화 제품을 고르기 전에 다음 질문을 답한다.

1. 보호할 것은 장치 전체인가, 특정 프로젝트인가, 이동식 매체인가, 장기 보관 백업인가?
2. 상대는 우연한 습득자, 절도범, 내부 관리자, 악성코드 운영자, 포렌식 역량을 가진 조직 중 누구인가?
3. 상대가 장치를 한 번만 얻는가, 돌려준 뒤 다시 쓰게 만드는가, 실행 중 접근하는가?
4. 기밀성·무결성·가용성 중 무엇을 우선하는가?
5. 키를 잃었을 때 데이터 소실을 감수할 수 있는가?
6. 여러 사람이 접근해야 하는가? 퇴사·역할 변경 시 어떻게 철회할 것인가?
7. 법률·계약·감사·증거 보전 요구가 있는가?
8. 장치가 지원 종료 전에 교체되는가? 복구 환경과 드라이버는 유지되는가?

고위험 표적은 장치 분실뿐 아니라 이블 메이드 공격, 부팅 체인 변경, 관리자 권한 탈취와 키 입력 관찰을 포함할 수 있다. 반대로 일반 개인에게 지나치게 복잡한 분리 키 체계는 백업 실패와 영구 소실을 만들 수 있다. 통제 강도는 위협과 운영 능력에 비례해야 한다.

## 4. 암호화 계층 설계

### 4.1 전체 디스크 암호화

전체 디스크 암호화는 운영체제, 사용자 파일, 스왑과 일부 임시 데이터를 넓게 보호하는 기본선이다. Windows에서는 BitLocker, macOS에서는 FileVault, Linux에서는 일반적으로 LUKS/dm-crypt 계열을 검토한다. 관리형 환경에서는 복구키 에스크로, TPM 사용 방식, 부팅 무결성, 정책 강제와 감사 가능성까지 포함한다.

TPM에 키를 봉인하면 정상 부팅의 편의성과 무결성 검사를 결합할 수 있지만, 자동 부팅만으로 고위험 오프라인 공격을 충분히 막는다고 가정하지 않는다. 위협 모델에 따라 PIN 또는 별도 시작 인증을 검토한다. 다만 매 부팅마다 복잡한 절차를 강제해 사용자가 장치를 항상 켜 두게 만들면 보호 상태가 오히려 약해질 수 있다.

### 4.2 파일·폴더·컨테이너 암호화

프로젝트 단위 경계, 외부 매체, 클라우드 동기화 전 암호화에는 컨테이너나 파일 단위 암호화가 유용하다. VeraCrypt 볼륨은 이 범주에 속한다. 컨테이너는 크기, 마운트 시점, 백업 방법, 동시 수정과 손상 복구를 설계해야 한다. 동기화 폴더에서 큰 컨테이너 하나를 계속 변경하면 충돌과 전송 비용이 커질 수 있다.

파일 단위 암호화는 파일명·크기·수정 시각·폴더 구조 같은 메타데이터를 얼마나 숨기는지 구현마다 다르다. 암호화 전에 생성된 미리보기, 최근 문서 목록, 검색 인덱스, 썸네일, 자동 저장본과 인쇄 스풀도 별도로 확인한다.

### 4.3 이동식 매체

USB SSD와 플래시 매체는 분실 가능성이 높고 여러 단말에 연결되므로 공격 면도 넓다. 하드웨어 암호화 제품을 사용할 때는 펌웨어 업데이트, 잠금 정책, 지원 종료, 복구 방식, 독립 평가의 범위를 확인한다. “하드웨어 암호화”라는 라벨만으로 구현 품질을 추정하지 않는다.

이동식 매체는 승인 단말에서만 사용하고, 자동 실행을 끄며, 파일 유입은 [모바일과 물리보안](../03_기기와-플랫폼/03_모바일과-물리보안.md)과 [파일 수신 검증](04_파일-수신-검증-공유.md)을 따른다. 암호화된 매체도 악성 파일을 안전하게 만들지 않는다.

### 4.4 백업 암호화

백업은 운영 장치보다 오래 남고 여러 위치에 복제된다. 백업 키를 원본 장치에만 두면 장치 고장과 함께 복구 능력을 잃고, 백업 옆에 평문으로 두면 분리의 의미가 없다. 백업 세트마다 키 식별자, 생성일, 복구 시험일과 폐기 예정일을 기록한다. 랜섬웨어 대응을 위해 쓰기 격리·버전 관리·불변 보존을 암호화와 별도로 설계한다.

## 5. VeraCrypt의 올바른 위치

VeraCrypt는 유지되는 공개 문서와 소스가 있는 다중 플랫폼 볼륨 암호화 도구다. 그러나 “완전한 암호”나 모든 환경의 최상위 해법으로 표현해서는 안 된다.

### 5.1 적합한 사용 사례

- 이동식 매체에 운영체제와 독립된 암호화 경계가 필요한 경우
- 특정 프로젝트를 별도 볼륨으로 마운트·해제하려는 경우
- 지원되는 환경에서 기존 워크플로와 상호운용성을 확인한 경우
- 복구 헤더, 백업과 버전 호환성을 관리할 수 있는 경우

### 5.2 주요 한계

- 볼륨을 마운트한 동안 사용자 권한 또는 관리자 권한을 가진 악성코드는 평문에 접근할 수 있다.
- 키 파일과 암호를 같은 장치·같은 계정에 두면 요소 분리가 약하다.
- 컨테이너 헤더 손상, 동기화 충돌, 갑작스러운 전원 차단은 가용성 문제를 만든다.
- 숨김 볼륨과 그럴듯한 부인 가능성은 운용 패턴, 외부 사본, 법적 맥락을 지우지 않는다. 보장으로 서술하지 않는다.
- 메모리, 최대 절전 모드, 크래시 덤프, 임시 파일과 애플리케이션 기록을 별도로 다뤄야 한다.

### 5.3 운영 기준

공식 배포 경로와 서명·해시 확인 절차를 기록한다. 볼륨 생성 시 알고리즘 이름보다 충분한 암호 엔트로피, 안전한 난수원, 파일시스템 호환성과 복구 가능성을 먼저 본다. 헤더 백업은 암호문과 분리해 보호하고 정기적으로 읽기 전용 복구 시험을 한다. 자동 마운트와 암호 캐시는 최소화하되, 지나친 불편 때문에 사용자가 평문 사본을 만들지 않는지 관찰한다.

## 6. BitLocker, FileVault, LUKS/dm-crypt

### 6.1 BitLocker

BitLocker는 Windows 플랫폼의 부팅·복구·관리 체계와 통합된다. 사용 중인 Windows 에디션과 하드웨어에서의 지원, 암호화 방식, TPM·PIN 정책, 복구키 저장 위치, 조직 관리자가 키에 접근하는 조건, 장치 암호화 자동 활성화 여부와 실제 보호 상태를 평가한다.

개인 Microsoft 계정이나 조직 디렉터리에 복구키가 보관되는 구성은 복구성을 높이는 대신 추가 신뢰 주체를 만든다. 이것이 허용되는지는 데이터 분류와 조직 정책으로 결정한다. `manage-bde -status` 또는 공식 관리 인터페이스로 볼륨 상태를 확인하고, 설정 화면의 체크 표시만 증거로 삼지 않는다.

### 6.2 FileVault

FileVault는 macOS의 저장 암호화와 계정·복구 체계에 통합된다. 개인 복구키 또는 기관 복구 절차를 어떻게 보관할지 정하고, 등록 사용자와 보안 토큰 상태를 관리한다. iCloud나 MDM에 대한 조직의 정책, Apple silicon·Intel 세대 차이와 현재 공식 문서를 확인한다. 잠금 해제된 로그인 세션과 클라우드 동기화 데이터는 별도 경계다.

### 6.3 LUKS/dm-crypt

Linux에서는 배포판 설치기의 LUKS/dm-crypt 통합이 일반적인 선택이다. 파티션 구조, `/boot`와 EFI 영역, TPM 연동, initramfs, 최대 절전 모드, 키 슬롯, 복구 매체를 함께 설계한다. 키 슬롯은 교체와 비상 접근을 돕지만, 사용하지 않는 키 슬롯과 이전 자격 증명을 방치하면 철회가 불완전해진다. 배포판의 지원 절차를 우선하고 독자적인 부팅 스크립트는 복구 부담을 계산한 뒤 사용한다.

## 7. Nitrokey Storage 2와 Nitrokey 계열

### 7.1 Nitrokey Storage 2를 정확히 분류하기

Nitrokey Storage 2는 암호화 저장 영역과 스마트카드 기능을 제공하는 특정 세대의 장치다. 제품 세대가 오래되거나 판매·지원 상태가 변할 수 있으므로 신규 도입 시 현재 공식 문서, 펌웨어 지원과 운영체제 호환성을 먼저 확인한다. 공개 소스는 검토 가능성을 높이지만 제조·배포·업데이트·호스트 소프트웨어의 데이터 처리를 자동으로 증명하지 않는다.

보유 장치를 계속 사용할 때는 다음을 문서화한다.

1. 정확한 모델·하드웨어 리비전·펌웨어 버전
2. 암호화 저장소와 OpenPGP 등 활성 애플리케이션
3. 관리자 PIN·사용자 PIN·재시도 및 잠금 정책
4. 초기화와 복구가 데이터에 미치는 영향
5. 호스트 도구의 설치 출처와 업데이트 방식
6. 분실 시 철회할 계정·키·인증서 목록
7. 고장 시 대체 장치로 복원하는 절차와 시험 결과

### 7.2 Nitrokey 3 등 현대 보안 키

Nitrokey 3 계열은 일반 파일 저장 장치가 아니라 모델·펌웨어가 지원하는 인증 애플리케이션을 중심으로 평가한다. FIDO2/WebAuthn 자격 증명, OpenPGP 키, OTP 등은 프로토콜과 복구 방식이 서로 다르다. 하나의 장치에 여러 역할을 집중하면 휴대는 편하지만 분실·고장이라는 공통 실패 원인이 생긴다.

보안 키를 쓸 때는 주 키와 동일하게 등록된 예비 키를 별도 위치에 두고, 서비스별 복구 코드와 관리자 철회 절차를 마련한다. 예비 키는 포장 상태로 방치하지 말고 실제 로그인 시험을 한다. 펌웨어 업데이트가 가능한지, 업데이트가 저장 자격 증명에 어떤 영향을 주는지도 공식 문서에서 확인한다.

## 8. YubiKey와 인증 용도 분리

YubiKey는 단일 기능의 제품명이 아니라 여러 모델과 폼팩터의 제품군이다. 일부 모델은 FIDO2/WebAuthn, U2F, OTP, PIV, OpenPGP 등을 지원하지만 모든 모델이 모든 기능을 제공하지 않는다. NFC 또는 USB-C 같은 인터페이스, 생체 기능, FIPS 검증 여부도 모델별이다. 구매 전 서비스가 요구하는 프로토콜과 정확한 모델의 기능표를 대조한다.

### 8.1 FIDO2/WebAuthn

피싱 저항성이 필요한 계정에는 서비스가 지원할 경우 FIDO2/WebAuthn 또는 패스키를 우선 검토한다. 검증자는 등록된 출처와 자격 증명을 확인하므로 사용자가 가짜 사이트에 OTP를 전달하는 위험을 줄일 수 있다. 다만 동기화형 패스키와 장치 귀속형 자격 증명은 백업·복구·관리 모델이 다르다.

### 8.2 TOTP·벤더 OTP

시간 기반 OTP는 폭넓게 지원되지만 사용자가 피싱 사이트에 코드를 입력할 수 있다. 시드가 앱·클라우드에 어떻게 저장·백업되는지, 장치 교체 시 어떻게 복원하는지 평가한다. Authy, Aegis, Google Authenticator 같은 앱 이름만으로 안전성을 서열화하지 않는다. 내보내기, 잠금, 백업 암호화, 지원 플랫폼, 업데이트와 계정 복구를 요구사항에 맞춰 비교한다.

### 8.3 PIV·OpenPGP

PIV와 OpenPGP 애플리케이션은 인증서 로그인, 서명, 암호화 키의 하드웨어 보관에 사용할 수 있다. PIN, 관리 키, 터치 정책, 인증서 수명, 폐기 목록과 키 백업 여부를 결정해야 한다. 서명 키와 암호화 키는 손실의 영향이 다르다. 서명 키는 복제하지 않는 정책이 가능하지만, 과거 암호문을 풀어야 하는 암호화 키는 조직의 에스크로 또는 안전한 백업이 필요할 수 있다.

## 9. 모바일 장치 암호화

현대 Android와 iOS는 저장 암호화와 하드웨어 보안 기능을 플랫폼에 통합한다. 2015년·2016년식 메뉴 경로를 고정 지침으로 유지하는 것은 위험하다. 제조사, OS 버전, 관리 정책과 잠금 방식에 따라 동작이 달라진다.

### 9.1 공통 기준

- 지원 중인 OS와 보안 업데이트 수준을 유지한다.
- 짧은 PIN보다 추측 비용이 높은 암호·긴 PIN을 사용하되 일상 사용성을 고려한다.
- 생체 인증은 편의 요소로 보고, 재부팅·장시간 미사용·정책 조건에서 강한 자격 증명이 요구되는지 확인한다.
- 잠금 화면 알림, USB 데이터 연결, 개발자 옵션, 디버깅, 백업과 클라우드 동기화를 검토한다.
- 분실 모드와 원격 삭제는 네트워크 연결과 계정 통제에 의존한다. 실행 성공을 보장하지 않는다.
- 장치가 잠금 해제된 상태에서 탈취되거나 악성 앱이 권한을 얻는 상황은 저장 암호화만으로 해결되지 않는다.

### 9.2 전원 차단 판단

고위험 상황에서 전원을 끄면 장치가 다시 강한 최초 잠금 해제를 요구하도록 전환될 수 있다. 그러나 갑작스러운 종료는 데이터 손상과 가용성 저하를 만들고, 사고 조사에서는 휘발성 증거를 잃게 한다. 조직 단말은 개인이 임의로 파괴하거나 초기화하지 말고 사고 대응 절차를 따른다. 생명·신체 안전이 걸린 상황은 기술 자산보다 사람의 안전을 우선한다.

## 10. 암호와 키 자료 생성

### 10.1 사람이 기억하는 암호

길이와 무작위성이 중요하다. 임의 생성한 여러 단어의 패스프레이즈나 암호 관리자가 생성한 고유 암호를 사용한다. “대문자·소문자·숫자·특수문자 16자리” 같은 형식 규칙은 최소선일 수 있으나 예측 가능한 치환과 재사용을 막지 못한다. 오프라인 공격 가능성이 큰 볼륨 암호는 온라인 로그인보다 더 높은 추측 저항성이 필요하다.

### 10.2 키 파일과 복구 코드

키 파일은 암호에 추가할 수 있지만, 같은 노트북의 같은 폴더에 두면 실질적인 요소 분리가 아니다. 키 파일을 잃으면 강한 암호를 알아도 복구할 수 없으므로 백업과 식별 체계가 필요하다. 복구 코드는 일회성인지, 사용 후 재발급되는지, 관리자가 무효화할 수 있는지 서비스별로 기록한다.

### 10.3 난수와 독자 암호 금지

운영체제와 검증된 라이브러리의 암호학적 난수 생성기를 사용한다. 사용자가 주사위 결과를 옮겨 적는 절차는 오류 검증까지 설계되지 않았다면 일반 사용자 기준으로 권장하지 않는다. 알고리즘을 직접 조합하거나 암호문을 다시 인코딩하는 것은 암호 강도를 입증하지 않는다.

## 11. 키 수명주기

### 11.1 생성

키 목적, 소유자, 생성 환경, 알고리즘·매개변수, 생성일, 만료 또는 검토일을 기록한다. 비밀 키 자체를 티켓·위키·일반 로그에 붙이지 않는다. 장치 내부 생성 키는 내보낼 수 있는지, 백업 불가인지 명시한다.

### 11.2 등록과 배포

공개키·인증서·보안 키를 계정에 등록할 때 대상 서비스와 계정을 상호 확인한다. 예비 키와 복구 수단을 동시에 등록하고, 등록 이벤트 알림을 보존한다. 대면 전달이나 별도 채널 확인 등 신뢰할 수 있는 배포 방법을 정한다.

### 11.3 사용

최소 권한과 목적 분리를 적용한다. 같은 개인 키를 인증·서명·암호화와 여러 조직에서 무분별하게 재사용하지 않는다. PIN 재시도, 터치 요구, 자동 잠금과 세션 시간을 설정한다. 관리 작업은 일반 브라우징과 분리된 단말 또는 프로필에서 수행한다.

### 11.4 교체와 철회

정기 교체만으로 안전해지는 것은 아니다. 노출 의심, 담당자 변경, 알고리즘·제품 지원 종료, 장치 분실과 정책 변경을 교체 조건으로 둔다. 새 키 배포, 기존 데이터 재암호화, 인증서 폐기, 캐시와 백업의 이전 키 처리까지 완료해야 한다. ‘새 키 생성’만으로 교체가 끝나지 않는다.

### 11.5 폐기

암호화 키 폐기는 관련 암호문을 사실상 읽을 수 없게 만들 수 있으므로 승인과 보존 의무를 확인한다. 플래시 저장장치는 덮어쓰기의 물리적 보장을 단순 가정하지 않는다. 전체 장치 암호화가 미리 적용된 경우 키 폐기와 제조사 보안 삭제 기능을 검토하며, 고위험 매체의 물리 폐기는 승인된 업체·증적 절차를 따른다.

## 12. 복구 설계

복구는 암호화의 예외가 아니라 일부다. 다음 세 가지 실패를 각각 시험한다.

1. **사용자 암호를 잊음**: 승인된 복구키로 복원하고 사용자 자격 증명을 재설정할 수 있는가?
2. **보안 키 분실·고장**: 예비 키 또는 복구 코드로 들어간 뒤 잃은 키를 철회할 수 있는가?
3. **운영체제·장치 고장**: 새 장치와 깨끗한 환경에서 암호화 백업을 복원할 수 있는가?

복구 자료는 봉인, 이중 통제, 접근 기록 또는 비밀 분할을 위험에 맞게 사용한다. 그러나 복잡한 비밀 분할은 참여자 부재와 절차 망각을 만든다. 복구 목표 시간과 허용 데이터 손실을 먼저 정하고 가장 단순하게 충족하는 방식을 택한다.

조직은 복구키 조회 권한자와 사유 기록, 긴급 접근 승인, 사후 검토를 정의한다. 개인은 서로 다른 물리적 위치의 백업, 신뢰할 수 있는 비상 연락 또는 상속 계획을 고려한다. 어느 경우든 실제 평문 복원 후 데이터 무결성을 확인하는 시험이 필요하다.

## 13. 구축 기준선

### 13.1 일반 개인

1. 지원 중인 OS와 내장 전체 디스크 암호화를 활성화한다.
2. 고유한 로그인 암호와 암호 관리자를 사용한다.
3. 주요 계정에 FIDO2/WebAuthn 또는 패스키를 등록하고 예비 수단을 둔다.
4. 민감 프로젝트만 별도 암호화 컨테이너를 사용한다.
5. 암호화된 자동 백업과 분리 백업을 구성하고 분기별 복원을 시험한다.

### 13.2 소규모 팀

장치 암호화 준수 상태, 복구키 보관, 입·퇴사 시 키 회수, 공유 비밀 저장소, 백업 복구와 사고 시 철회 절차를 중앙 기준으로 둔다. 개인 메신저나 문서에 공유 암호를 남기지 않는다. 관리자가 모든 평문에 상시 접근하는 구조가 필요한지 최소화한다.

### 13.3 고위험 표적

위협 모델에 따라 Qubes 같은 격리 플랫폼, 오프라인 키 생성, 장치 귀속 보안 키, 최소 데이터 여행용 단말, 이블 메이드 탐지와 엄격한 물리 통제를 조합한다. 통제마다 실패 시 대체 경로를 문서화한다. 유명 제품을 여러 개 겹치는 것으로 고위험 설계를 대신하지 않는다.

## 14. 검증 절차와 증적

### 14.1 상태 검증

- 모든 내부 볼륨과 이동식 매체의 암호화 상태를 공식 명령 또는 관리 콘솔로 확인한다.
- 재부팅 후 최초 인증 전 데이터 접근이 차단되는지 시험한다.
- 최대 절전·절전·잠금 상태의 차이를 기록한다.
- 복구키가 지정된 위치에 있고 승인된 사람만 읽을 수 있는지 확인한다.
- 평문 임시 파일, 동기화 사본, 로그, 크래시 덤프와 스왑을 표본 검사한다.

### 14.2 복구 검증

생산 데이터를 손상시키지 않는 시험 장치나 복제본으로 분기별 복구를 수행한다. 시험 기록에는 날짜, 시험자, 제품·버전, 키 식별자, 복구 시간, 오류와 후속 조치를 남긴다. ‘백업 파일이 존재함’은 복구 성공 증거가 아니다.

### 14.3 보안 키 검증

- 주 키와 예비 키로 각각 로그인한다.
- 잃은 키 한 개를 시험 계정에서 철회하고 재사용이 거부되는지 확인한다.
- PIN 잠금과 초기화 절차를 시험용 장치에서 확인한다.
- 인증서·OpenPGP 키의 만료와 폐기 경로를 확인한다.
- NFC·USB 등 사용하지 않는 인터페이스를 끌 수 있는지 모델별로 검토한다.

### 14.4 실패 판정

다음 중 하나면 통제가 구축됐다고 판정하지 않는다.

- 복구키가 암호화된 장치 안에만 있다.
- 예비 보안 키가 등록되지 않았거나 시험되지 않았다.
- 사용자가 불편 때문에 평문 사본을 개인 클라우드에 만든다.
- 마운트된 볼륨이 로그아웃·절전 후에도 예상보다 오래 열린다.
- 담당자가 제품 모델, 펌웨어, 키 목적과 철회 절차를 설명하지 못한다.
- 암호화 상태는 보이지만 실제 복원 시험 기록이 없다.

## 15. 사고 대응

보안 키나 암호화 장치 분실 시 장치 찾기에만 집중하지 않는다. 관련 계정 세션 종료, 자격 증명 철회, 인증서 폐기, 복구 코드 재발급과 영향 데이터 식별을 병행한다. 장치가 잠금 해제된 상태였거나 악성코드가 의심되면 키가 추출되지 않았다고 단정하지 말고 새 키로 전환한다.

랜섬웨어·침해 상황에서는 임의 초기화 전에 증거 보전과 사업 영향 판단을 한다. 개인 안전이 위협받는 상황에서는 조직의 장치 보전보다 대피와 신고를 우선한다. 법 집행 회피나 증거 파괴를 목적으로 한 자동 파괴 장치를 설계하지 않는다.

## 16. 잔여 위험

암호화는 사용자가 평문을 읽고 편집하는 순간의 공격을 제거하지 않는다. 공급망, 펌웨어, 키로거, 화면 촬영, 악성 확장, 원격 관리, 협업 상대와 클라우드 계정은 계속 위험으로 남는다. 강한 암호화는 키 분실 시 가용성 손실을 더 확실하게 만든다. 따라서 단말 보안, 최소 권한, 패치, 로그, 데이터 최소화, 백업과 사고 대응이 함께 작동해야 한다.

제품의 공개 소스, 보안 인증, 외부 감사는 중요한 증거지만 ‘백도어 없음’이나 미래 안전의 증명은 아니다. 평가 범위·버전·기간과 발견 사항의 조치 여부를 읽어야 한다. 신규 취약점, 지원 종료와 조직의 사용 방식이 바뀌면 판단도 다시 해야 한다.
