# VPN, Tor, 프록시

> VPN과 Tor는 ‘익명성 버튼’이 아니다. 네트워크에서 누가 무엇을 볼 수 있는지, 신뢰가 어느 주체로 이동하는지, 연결이 실패할 때 실제 트래픽이 어디로 흐르는지를 바꾸는 도구다. 제품을 겹치는 것보다 관찰자·단말·계정·시간 상관관계를 분리하는 설계가 먼저다.

## 1. 공격자 관점의 네트워크 경계

공격자는 VPN·Tor의 암호를 깨기보다 연결 전후의 트래픽, 동일 쿠키·계정, DNS·IPv6 우회, 브라우저 밖 애플리케이션, 결제·복구 정보와 활동 시간을 결합한다. Mullvad, Proton VPN, Tor, OpenVPN, WireGuard와 킬 스위치는 이 관찰면 일부를 바꾸지만 신뢰와 식별자를 제거하지 않는다.

이 장은 Mullvad와 Proton VPN을 공급자 평가 사례로 삼고 WireGuard·OpenVPN, Tor Browser, 프록시와 킬 스위치를 다음 기준으로 분석한다.

- 유료라는 사실은 안전의 증거가 아니고, 무료라는 사실만으로 악성이라고 단정할 수도 없다. 수익 구조, 데이터 처리, 구현, 업데이트와 검증 범위를 평가한다.
- “유출 기록이 없다”는 공개 정보와 특정 시점 감사의 범위를 넘는 주장이다. 감사는 대상 시스템·기간·버전을 읽어야 한다.
- VPN과 Tor를 겹친다고 이점이 자동으로 합산되지 않는다. 순서와 장애 동작에 따라 새로운 신뢰·식별·가용성 위험이 생긴다.
- OpenVPN은 검증된 프로토콜 선택지지만, 프로토콜 이름만으로 킬 스위치와 누출 방지가 완성되지 않는다.

**한 번의 실제 IP 연결과 동일 계정·쿠키 재사용만으로도 분리된 활동이 연결될 수 있다.** 이는 VPN 제품보다 세션·브라우저·운영 경계의 문제다.

## 2. 보호 목표를 먼저 정한다

같은 VPN이라도 목표가 다르면 성공 조건이 다르다.

1. 공용 Wi-Fi에서 로컬 도청과 변조 위험을 낮춘다.
2. ISP가 개별 목적지와 DNS 요청을 직접 관찰하는 범위를 줄인다.
3. 목적지 서비스에 주거용 IP 대신 공유 출구 IP를 보인다.
4. 조직 내부 자원에 인증된 경로로 접속한다.
5. 검열 환경에서 연결 가능성을 확보한다.
6. 조사·취재 활동의 출발 네트워크와 목적지를 분리한다.
7. 일반 브라우징과 별도 역할의 계정·세션을 분리한다.

목표 1~4는 상용 또는 조직 VPN으로 충족할 수 있지만, 목표 6은 Tor Browser, 전용 환경, 계정 분리와 행동 규칙이 필요할 수 있다. 목표 7은 네트워크 도구보다 브라우저 프로필·VM·Qubes 구획이 더 중요한 통제일 수 있다.

“IP를 숨긴다”는 표현만으로는 검증할 수 없다. 다음처럼 쓴다.

> 공용 무선망과 ISP에서는 단말과 VPN 게이트웨이 사이의 암호화된 연결 및 게이트웨이 주소가 관찰된다. 목적지에는 VPN 출구 주소가 표시된다. VPN 운영자는 연결 메타데이터와 출구 트래픽의 일부를 관찰할 위치에 있으며, 목적지 계정·쿠키와 단말 침해는 별도로 남는다.

## 3. 관찰자와 데이터 흐름

### 3.1 VPN을 사용하지 않을 때

HTTPS를 올바르게 사용해도 로컬 네트워크와 ISP는 출발 IP, 통신 상대에 관한 일부 메타데이터, 시간·용량·빈도를 관찰할 수 있다. DNS 보호 방식, TLS 버전, ECH 지원과 서비스 구조에 따라 보이는 범위가 달라진다. 목적지는 출발 공인 IP, 계정, 쿠키, 브라우저 지문과 요청 내용을 볼 수 있다.

### 3.2 VPN을 사용할 때

로컬 네트워크와 ISP의 직접 관찰 대상은 주로 VPN 게이트웨이와의 터널로 바뀐다. VPN 운영자는 가입·결제·연결 정보와 출구 측 트래픽을 처리할 위치에 놓인다. 목적지는 VPN 출구 IP를 보지만 로그인 계정, 쿠키, 브라우저 특성, 요청 내용과 사용 시간은 여전히 관찰할 수 있다.

따라서 VPN은 신뢰를 제거하지 않고 **이동·집중**한다. ISP와 목적지 사이에 VPN 사업자가 새로운 신뢰 주체로 들어온다. 다수 사용자가 공유 출구를 쓰면 IP 기반 구분은 어려워질 수 있지만, 계정과 지문이 그대로면 활동은 여전히 연결된다.

### 3.3 Tor Browser를 사용할 때

Tor는 트래픽을 여러 중계로 전달해 단일 중계가 출발지와 최종 목적지를 동시에 알기 어렵게 설계한다. 입구 측에서는 Tor 사용 사실 또는 브리지 연결이 보일 수 있고, 목적지에는 Tor 출구가 보인다. HTTPS가 아닌 트래픽은 출구 이후 평문 위험이 있으므로 현대 웹에서는 HTTPS 상태를 확인한다.

Tor Browser는 네트워크 경로뿐 아니라 브라우저 특성을 사용자 집단과 비슷하게 유지하려 한다. 확장 설치, 고유 글꼴, 창 크기·설정의 과도한 변경, 외부 프로그램으로 파일 열기와 실명 계정 로그인은 이 목적을 약화할 수 있다.

## 4. VPN 사업자 평가

### 4.1 소유와 관할

법인명, 실질적 소유 구조, 운영 국가, 데이터 요청을 받는 법적 절차와 투명성 보고를 확인한다. 관할만 보고 안전을 단정하지 않는다. 서버가 여러 국가에 있고 결제·지원·분석 하청이 다른 관할에 있을 수 있다.

### 4.2 계정과 결제

이메일 없이 번호형 계정을 제공하는지, 결제 수단이 어떤 기록을 남기는지, 환불·사기 방지·세금 처리를 위해 무엇을 보존하는지 확인한다. 제3자 판매자나 현금 결제는 결제 연결성을 줄일 수 있지만 공급망 사기, 계정 재판매와 지원 곤란을 추가한다. 정당한 사용에서 결제 기록 자체를 위험으로 가정할 필요는 없다.

### 4.3 로그 정책

“노로그” 문구만 보지 않는다. 다음 항목별 보존 여부와 기간을 찾는다.

- 가입 식별자와 결제 기록
- 접속 시각, 세션 시간, 사용량
- 출발 IP와 할당된 출구 IP 또는 포트
- DNS 요청, 목적지, 오류·진단 로그
- 앱 충돌 보고, 분석 SDK, 고객 지원 첨부 파일
- 남용 대응과 법적 요청 처리 기록

정책은 기술적 구조와 일치해야 한다. 서버가 필요한 데이터를 생성하지 않는지, 중앙 관리가 어떤 메타데이터를 받는지, 진단 기능이 기본 활성인지 살핀다.

### 4.4 독립 감사와 공개 소스

감사 보고서에는 발주자, 수행자, 날짜, 대상 앱·서버·인프라, 샘플 범위, 제한, 발견 사항과 개선 재시험이 있어야 한다. 한 번의 앱 감사는 전체 운영과 이후 버전을 보증하지 않는다. 공개 소스 앱은 재현 가능한 빌드, 배포 서명과 실제 서버 운영까지 자동 증명하지 않는다.

### 4.5 서버와 네트워크

서버 소유·임대 방식, 디스크리스 운영 여부, 관리 접근, 키 교체, 업데이트, 침해 대응, IPv6와 DNS 처리, 포트 포워딩 정책을 확인한다. “RAM only”는 재부팅 후 로컬 상태 감소에 도움이 될 수 있지만 제어 계층과 외부 로그까지 없다는 뜻은 아니다.

## 5. Mullvad와 Proton VPN을 평가 사례로 다루기

### 5.1 Mullvad

Mullvad는 번호형 계정, 공식 앱, WireGuard·OpenVPN 지원과 공개된 감사·보안 자료로 평가 가능한 선택지다. 2022년 서버 감사는 특정 범위와 시점에서 고객 데이터 로깅과 누출을 점검한 증거다. 이를 모든 시기와 시스템의 무유출 증명으로 확장하지 않는다.

도입 시 현재 개인정보 처리방침, 최신 앱·인프라 감사, 지원 프로토콜, 포트 포워딩 등 기능 변경, 결제 방식과 사용 플랫폼의 공식 문서를 다시 확인한다. 계정 번호를 공개 채널이나 지원 캡처에 남기지 않는다. 동일 계정을 여러 역할에서 공유하면 결제 정보가 없더라도 내부적으로 사용 패턴이 연결될 수 있다.

### 5.2 Proton VPN

Proton VPN은 무료 등급과 유료 기능, 공개 앱과 감사 자료를 제공하는 서비스 사례다. 무료 등급이라는 이유만으로 위험하다고 단정하지 않고, 무료 서비스의 재원과 제한·데이터 처리를 공식 정책으로 확인한다. Proton 계정이 Mail 등 다른 서비스와 결합될 때 계정 복구와 활동 연결성이 보호 목표에 맞는지 검토한다.

각 서비스의 감사와 투명성 자료는 현재 버전과 일치하는지 확인한다. 두 제품을 동시에 구독하거나 연쇄 연결해도 계정·브라우저·단말 분리가 없으면 실질적 익명성이 자동 증가하지 않는다.

## 6. WireGuard와 OpenVPN

### 6.1 WireGuard

WireGuard는 비교적 작은 프로토콜·구현 설계와 현대 암호 조합을 지향한다. 일반적으로 운영체제 통합과 빠른 연결 복구가 장점이 될 수 있다. 정적 공개키와 주소 할당을 서비스가 어떻게 관리하는지, 로밍과 연결 상태가 어떤 로그를 만드는지, 앱이 DNS·라우팅·킬 스위치를 어떻게 구현하는지 확인한다.

### 6.2 OpenVPN

OpenVPN은 TLS 기반으로 폭넓게 배포되어 있고 다양한 전송·인증 구성이 가능하다. 유연성은 잘못된 구성 가능성도 뜻한다. 오래된 암호군, 인증서 검증 누락, 압축, 스크립트 훅, 자격 증명 파일 권한과 설정 파일 유출을 점검한다. 공급자가 제공한 설정을 임의 수정하기 전에 지원 문서를 확인한다.

### 6.3 선택 기준

프로토콜은 다음 요구로 선택한다.

- 사용 플랫폼의 공식 지원과 업데이트
- 네트워크 전환 후 재연결 동작
- 검열·차단 환경에서의 연결성
- DNS·IPv6·분할 터널 처리
- 인증서·키 수명주기와 장치 철회
- 조직 방화벽과 감시 정책
- 운영자가 실제로 시험하고 장애를 진단할 수 있는가

속도 측정만으로 선택하지 않는다. 안전한 기본값과 실패 시 닫힘 동작이 더 중요할 수 있다.

## 7. 킬 스위치와 Always-on

킬 스위치는 VPN 연결이 없을 때 허용되지 않은 인터페이스로 트래픽이 나가지 않도록 라우팅·방화벽을 제어하는 기능이다. 앱의 버튼 이름이 아니라 실제 장애 시 동작을 시험한다.

### 7.1 실패 경로

- 앱 시작 전 부팅 초기 구간
- VPN 프로세스 충돌 또는 강제 종료
- Wi-Fi에서 유선·모바일 핫스팟으로 전환
- 절전 복귀와 네트워크 로밍
- IPv4 터널에서 IPv6가 별도로 나가는 경우
- DNS가 운영체제 기본 서버로 복귀하는 경우
- 로컬 프록시 또는 브라우저만 터널을 쓰는 경우
- 컨테이너·VM·Docker가 별도 네트워크 경로를 갖는 경우
- 분할 터널 예외 앱이 하위 프로세스를 실행하는 경우
- VPN 업데이트·제거 중 방화벽 규칙이 사라지는 경우

### 7.2 구현 원칙

고위험 환경에서는 애플리케이션이 연결 후 규칙을 추가하는 방식보다 운영체제 방화벽이 기본 거부하고 승인된 VPN 게이트웨이와 터널 인터페이스만 허용하는 구조를 검토한다. 그러나 원격 관리 서버에 잘못 적용하면 자신을 잠글 수 있으므로 콘솔 복구와 단계적 배포가 필요하다.

Always-on VPN과 킬 스위치는 다르다. Always-on은 자동 연결 의도를, 킬 스위치는 비연결 상태의 차단을 의미할 수 있다. 제품마다 용어가 다르므로 시험 결과로 판단한다.

## 8. DNS, IPv6, WebRTC와 기타 누출

### 8.1 DNS

VPN이 자체 DNS를 제공해도 운영체제의 다중 인터페이스, 브라우저의 DoH, 기업 에이전트와 로컬 캐시가 다른 경로를 사용할 수 있다. DNS 서버 주소뿐 아니라 실제 패킷의 인터페이스와 목적지를 관찰한다. 암호화 DNS는 질의 내용을 일부 구간에서 보호하지만 연결 시간·목적지 IP 등 다른 메타데이터를 없애지 않는다.

### 8.2 IPv6

IPv6를 무조건 끄는 것은 장기 해법이 아니다. VPN이 IPv6를 터널링·차단·지원하는 방식을 확인한다. IPv6 비활성화가 필요한 임시 구성이라면 업데이트나 네트워크 변경 뒤 되돌아가지 않는지 시험한다.

### 8.3 WebRTC와 브라우저 API

과거 브라우저의 WebRTC 주소 노출 문제 때문에 무조건 기능을 끄는 지침이 널리 퍼졌지만, 현재 동작은 브라우저·OS·VPN 구현에 따라 달라진다. 기능 차단이 화상회의를 깨거나 고유한 설정 지문을 만들 수 있다. 최신 공식 문서와 실제 시험으로 결정한다.

### 8.4 브라우저 밖 트래픽

업데이터, 클라우드 동기화, 메신저, 시간 동기화, 오류 보고, 운영체제 계정과 악성코드는 브라우저 프록시를 따르지 않을 수 있다. ‘브라우저에서 출구 IP 확인’만으로 단말 전체의 경로를 증명하지 않는다.

## 9. Tor Browser 운영

### 9.1 설치와 업데이트

Tor Project의 공식 배포 경로에서 받고 서명 검증 절차가 필요한 환경은 공식 안내를 따른다. 자동 업데이트를 허용하거나 명시적인 신속 업데이트 절차를 둔다. 오래된 Tor Browser를 고정하는 것은 알려진 취약점과 지문 차이를 키운다.

### 9.2 행동 경계

- 별도 역할에는 별도 Tor Browser 세션과 계정을 사용한다.
- 실명 계정 로그인은 출발 IP가 가려져도 신원을 서비스에 직접 알린다.
- 추가 확장과 임의 설정 변경을 최소화한다.
- 내려받은 문서를 외부 앱에서 열면 직접 네트워크 연결이나 외부 리소스 요청이 발생할 수 있다. 오프라인 또는 격리 환경에서 연다.
- 토렌트 클라이언트를 Tor 네트워크에 임의 연결하지 않는다. 프로토콜과 클라이언트가 주소를 노출하거나 네트워크에 부담을 줄 수 있다.
- Tor 출구 차단과 CAPTCHA는 가용성 문제다. 이를 우회하려고 실명 브라우저로 같은 세션을 이어가면 역할이 연결될 수 있다.

### 9.3 브리지와 검열 우회

브리지는 Tor 사용 사실을 숨기거나 차단을 우회하는 데 도움을 줄 수 있지만 모든 관찰자에게 탐지 불가능하다는 보장은 없다. 내장 전송 방식과 현재 공식 지원을 확인한다. 브리지 주소를 무분별하게 공개하면 차단 위험을 높일 수 있다.

### 9.4 남는 한계

강한 전역 관찰자는 시간·용량 상관을 시도할 수 있다. 악성 단말, 브라우저 취약점, 사용자가 제출한 개인정보, 상대방의 기록과 물리적 감시는 Tor가 제거하지 않는다. 저지연 익명 네트워크의 구조적 한계를 인정하고 완전한 불추적성을 주장하지 않는다.

## 10. VPN과 Tor의 조합

### 10.1 VPN 다음 Tor

단말이 VPN에 연결한 뒤 Tor를 쓰면 ISP는 보통 VPN 연결을 보고, VPN은 출발 IP와 Tor 진입 연결을 볼 위치에 있다. Tor 목적지는 VPN 출구가 아니라 Tor 출구를 본다. Tor가 차단된 네트워크에서 연결성에 도움이 될 수 있지만, VPN 계정과 결제·연결 기록이라는 신뢰 주체가 추가된다. Tor Browser의 브리지가 더 단순한 대안인지 비교한다.

### 10.2 Tor 다음 VPN

Tor를 통해 VPN에 연결하는 구조는 설정과 지원이 더 복잡하고, 고정 VPN 출구가 여러 Tor 세션을 연결하는 표지가 될 수 있다. VPN은 목적지 트래픽을 관찰할 위치에 있으며, 잘못된 라우팅과 DNS 구성 위험이 커진다. 명확한 요구와 검증 능력이 없다면 일반 기준선으로 권고하지 않는다.

### 10.3 다중 VPN

서로 다른 공급자를 연쇄 연결하면 단일 관찰 지점을 분산하려는 목적이 있을 수 있으나, 계정·결제·시간 정보와 장애 지점이 늘어난다. 한 공급자의 ‘멀티홉’은 운영 편의가 있지만 동일 사업자 신뢰를 분리하지 않는다. 체인 수가 아니라 각 홉의 관찰 범위, 독립성, 실패 시 경로를 그린다.

### 10.4 결론

“OpenVPN + Mullvad + Tor”를 모든 사용자에게 최적이라고 부르지 않는다. 일반 사용자는 최신 브라우저·HTTPS·신뢰할 수 있는 VPN과 계정 보안이 더 실용적일 수 있다. 익명 출판자는 Tor Browser와 별도 작업 환경을 우선할 수 있다. 조합은 위협 모델이 요구하고 반복 시험할 수 있을 때만 도입한다.

## 11. 프록시와 SSH 터널

HTTP·SOCKS 프록시는 특정 애플리케이션의 출구를 바꿀 수 있지만 단말 전체를 보호하지 않는다. 프록시 운영자는 처리하는 트래픽과 메타데이터를 볼 위치에 있다. 무료 공개 프록시는 소유·운영·무결성을 검증하기 어려우며 민감한 인증에 사용하지 않는다.

SSH 동적 포워딩은 신뢰하는 서버를 통해 일부 트래픽을 전달하는 관리 도구다. DNS를 원격에서 해결하는지, 애플리케이션이 SOCKS를 실제로 따르는지, 서버 로그와 계정 키를 관리해야 한다. 회사의 보안 통제를 우회하는 개인 터널은 정책·감사·사고 대응을 훼손하므로 승인 없이 만들지 않는다.

리버스 프록시와 CDN은 서버의 원본 IP를 가리는 용도로 쓰이지만, 원본 방화벽이 CDN 대역만 허용하지 않거나 DNS 역사·인증서·메일 헤더에 원본이 남으면 우회된다. 이는 사용자 VPN과 다른 주제이며 서버 노출 관리 문서에서 다룬다.

## 12. 계정·쿠키·행동 상관관계

네트워크 출구가 달라도 다음 표지가 같으면 활동이 연결될 수 있다.

- 동일 이메일, 전화번호, 복구 계정, 결제 수단
- 같은 브라우저 쿠키·로컬 저장소·광고 식별자
- 드문 브라우저 설정, 글꼴, 화면 크기, 확장 조합
- 문체, 언어, 맞춤법, 작업 시간대와 반복 행동
- 같은 파일의 메타데이터·해시·워터마크
- 한 계정이 실명 네트워크와 가명 네트워크를 오가는 로그인 기록
- 상대방 주소록과 클라우드 연락처 업로드

VPN 연결이 끊긴 한 번의 요청은 직접 연결고리가 될 수 있다. 그러나 이를 막는 핵심은 킬 스위치 하나가 아니라 역할별 브라우저·계정·단말 또는 VM, 데이터 이동 규칙, 재로그인 금지와 세션 폐기다. 분리된 역할 사이에서 링크를 복사하거나 같은 문서를 편집할 때도 메타데이터가 넘어갈 수 있다.

## 13. 참조 아키텍처

### 13.1 일반 개인·재택근무

지원 중인 OS, WPA2/3가 적용된 네트워크, HTTPS, 조직 또는 검토된 VPN, MFA와 암호 관리자를 기본으로 한다. 은행·공공 서비스처럼 VPN 출구를 차단하는 사이트는 별도 일반 프로필에서 이용하되, 가명 역할과 섞지 않는다.

### 13.2 소규모 조직

조직 관리 VPN 또는 ZTNA의 목적은 내부 자원 접근 통제와 장치 신뢰 확인이다. 상용 소비자 VPN으로 대체하지 않는다. SSO, 장치 인증서, 최소 권한, 로그 보존, 퇴사자 철회, 비상 접근과 용량 계획을 둔다. 분할 터널 여부는 데이터 흐름과 모니터링 요구로 결정한다.

### 13.3 조사·취재·고위험 출판

전용 사용자 또는 Qubes 구획, Tor Browser, 개인 활동과 분리된 계정, 문서 정화와 안전한 연락 채널을 사용한다. 출판 시점·문체·원본 파일 메타데이터가 신원을 드러낼 수 있으므로 네트워크 계층 밖 통제를 포함한다. 대상과 직접 연락할 때 상대방의 안전과 동의도 고려한다.

### 13.4 검열 환경

Tor 브리지, VPN의 난독화 기능 또는 승인된 우회 수단 중 현재 연결 가능한 것을 준비하되, 사용 자체가 법적·신체적 위험을 만들 수 있는 지역에서는 현지 위험 정보를 별도로 확인한다. 하나의 서비스에 의존하지 말고 사전에 설치·업데이트·연락 복구 절차를 준비한다.

## 14. 구축 절차

1. [위협 모델](../00_백서-안내/03_기준-위협-모델.md)에서 관찰자와 보호 목표를 선택한다.
2. 현재 네트워크 흐름과 DNS·IPv6·브라우저 밖 앱을 목록화한다.
3. 필요한 기능과 금지 조건으로 공급자·프로토콜을 비교한다.
4. 공식 앱과 배포 서명을 확인하고 최소 설정으로 설치한다.
5. 킬 스위치·Always-on·분할 터널의 의미를 문서화한다.
6. 정상 연결, 연결 실패, 재부팅, 절전 복귀, 네트워크 전환을 시험한다.
7. 역할별 계정·브라우저·VM 경계를 구축한다.
8. 로그·구독·키·예비 접속 경로와 사고 대응을 기록한다.
9. 30일 실제 사용에서 우회, 성능, 차단, 누출과 지원 사건을 수집한다.
10. 분기마다 정책·감사·앱 버전과 시험 결과를 재검토한다.

## 15. 검증 계획

### 15.1 기능 시험

- 기대한 출구 IP와 국가·서버가 표시되는가?
- DNS 요청이 설계한 경로로 흐르는가?
- IPv4와 IPv6 모두 같은 정책을 따르는가?
- 브라우저뿐 아니라 지정한 앱과 VM·컨테이너도 정책을 따르는가?
- 로컬 네트워크 접근이 필요한 경우 의도한 범위만 허용되는가?

### 15.2 장애 시험

승인된 시험 환경에서 VPN 프로세스 종료, 터널 인터페이스 비활성화, Wi-Fi 전환, 절전·복귀와 재부팅을 수행한다. 각 단계에서 패킷 캡처와 운영체제 라우팅·방화벽 상태를 확인한다. 외부 ‘누출 테스트’ 사이트 한 곳의 결과를 익명성 증명으로 사용하지 않는다.

### 15.3 세션 시험

역할 A 브라우저의 쿠키·다운로드·클립보드가 역할 B에 남지 않는지 확인한다. VPN 비연결 상태에서 역할 A 앱이 시작되지 않는지 시험한다. 계정 보안 페이지에서 로그인 IP·세션·시간이 기대와 일치하는지 확인하되, 서비스 표시가 네트워크 진실의 유일한 증거라고 가정하지 않는다.

### 15.4 증적 형식

시험일, 시험자, 장치·OS·VPN 앱 버전, 프로토콜, 서버, 네트워크 유형, 시나리오, 기대 결과, 관찰 결과, 패킷 또는 로그 위치와 후속 조치를 남긴다. IP와 계정 식별자는 공유 보고서에서 필요 최소한으로 마스킹한다.

### 15.5 실패 판정

다음 중 하나면 운영 배포를 중단하거나 단순화한다.

- VPN 연결 전후 동일한 역할 브라우저가 실제 네트워크로 요청한다.
- 재부팅 또는 업데이트 후 킬 스위치가 해제된다.
- DNS나 IPv6 경로가 설계와 반복적으로 다르다.
- 사용자가 차단 때문에 개인 브라우저로 민감 세션을 이어간다.
- 공급자 정책과 실제 앱의 진단·분석 동작을 설명할 수 없다.
- Tor Browser에 여러 확장과 고유 설정을 넣어 유지할 수 없다.
- 다중 홉 체인을 장애 시 누가 복구할지 정해져 있지 않다.

## 16. 사고 대응과 잔여 위험

실제 IP 노출, 잘못된 계정 로그인 또는 VPN 계정 침해가 의심되면 네트워크만 다시 연결하고 끝내지 않는다. 영향 세션을 종료하고, 관련 계정·쿠키·토큰을 철회하며, 역할 간 연결 가능성과 목적지 로그를 평가한다. VPN 자격 증명과 장치 키를 교체하고 공급자 공지를 확인한다. 고위험 활동은 새 역할 환경에서 재개할지 별도로 결정한다.

VPN과 Tor는 감염된 단말, 피싱, 계정 복구, 상대방의 스크린샷, 파일 워터마크, 시간·용량 상관, 물리 감시와 법적 절차를 제거하지 않는다. Tor 출구와 VPN 주소는 차단·추가 인증의 대상이 될 수 있다. 네트워크 프라이버시와 서비스 약관·현지 법률 준수는 함께 검토한다.

가장 강한 설계는 가장 많은 터널을 겹친 설계가 아니라, 목적을 설명할 수 있고 실패 상태를 반복 검증하며 사용자가 우회하지 않는 설계다.
